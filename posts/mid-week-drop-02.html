The CSV Problem 😅😅

When I first started building the telemetry platform, I needed somewhere to store all the data coming from FastF1. The obvious choice was CSV 🤷‍♂️… It’s simple, readable, easy to inspect, and almost every tool on Earth knows how to work with it.

For a small dataset, CSV is perfectly fine.

But F1 telemetry is not exactly a small dataset. A single session can contain data from multiple drivers, hundreds of laps, and thousands of telemetry points per lap. Once you start combining position, speed, throttle, brake, gear, RPM, time, and other information, the number of rows starts becoming ridiculous.

And my original thought process was basically…. “It’s just data. Put it in CSV. What could possibly go wrong?”

Famous last words.

The problem with CSV is that it stores everything as plain text. It doesn’t really care whether a column contains numbers, timestamps, or repeated values. It just stores the information row by row. That makes it convenient, but not particularly efficient when the dataset starts getting large.

And my project was supposed to become reusable.

I didn’t want to build a dashboard that only worked for one race, one session, or one driver. I wanted to eventually be able to select something like:

2025 → Abu Dhabi → Qualifying → Verstappen vs Norris

…and have the application load the correct data without me manually rewriting half the backend.

That meant the storage system also had to be designed for scale. So I started looking into better options and eventually landed on Parquet.

Parquet is a column-based storage format, which basically means it stores data by columns instead of treating every row as one giant block of text. That matters because telemetry usually involves selecting specific columns.

For example, if I only need:

  • Time
  • X and Y position
  • Speed
  • Throttle
  • Brake

…I shouldn’t have to load every single piece of information stored in the dataset just to display those values.

Parquet makes that kind of selective loading much more practical. It is also better suited for large structured datasets and generally handles compression more efficiently than plain CSV.

So instead of treating my telemetry data like a giant spreadsheet that I keep throwing more rows into, I started organising it into a proper dataset structure.

The idea is simple: each session should have its own data, and the backend should be able to discover what is available rather than relying on hardcoded filenames and assumptions. This is the point where the project started feeling less like:

“I made an F1 dashboard.”

…and more like:

“I’m actually building a platform that can support an F1 dashboard.”

Which is a much nicer way of saying I had to clean up the mess I created earlier. The CSV decision wasn’t the end of the world, but it was definitely one of those moments where I had to stop and ask myself:

“Was this a smart engineering decision, or did I just want the easiest option because I was excited to see the dashboard working?”

The answer was, unfortunately, both.
